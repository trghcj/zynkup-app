1. Product Overview
ZynkUp is an advanced, full-stack campus networking and event management platform designed to connect students, facilitate community building, and streamline campus event organization. In today's disconnected digital landscape, students often struggle to find relevant campus events, join localized communities, or securely chat with peers — ZynkUp solves this with a unified, cross-platform mobile and web application built on production-grade infrastructure.

1.1 Core Features
Feature	Description
JWT Authentication	Secure, token-based login/signup with bcrypt password hashing (cost factor 12). Tokens carry user_id + role claims; no DB hit on subsequent requests.
Role-Based Access Control	Three-tier model: Global Admins (platform moderation), Club Creators/Admins (club management & event creation), and regular Members (read + participate). Each route is protected by a dependency that decodes the JWT role claim.
Campus Clubs & Communities	Create clubs with custom banners hosted on Cloudinary CDN. Admins can manage member lists, assign roles dynamically, and pin announcements. Clubs have isolated chat rooms.
Real-Time Club Chat	Live WebSocket messaging (WSS protocol) with rich avatars, role badges (colour-coded), timestamps, and persistent chat history fetched on room entry.
Friend Connections	Bi-directional friend request system: Send Request → Accept/Decline. Accepted connections unlock direct messaging. All state stored relationally with proper FK constraints.
Gamified XP System	+5 XP on friend acceptance; +40 XP on club creation. XP feeds a streak counter and leaderboard. Designed to drive daily engagement and community participation.
Event Management	Browse upcoming campus events filtered by category, date, and location. Registered attendees receive a QR Pass (base64-encoded JWT payload) scanned at the venue for check-in.
Glassmorphism UI	Premium dark-mode aesthetic via Flutter's BackdropFilter + ImageFilter.blur(). Semi-transparent containers over gradient backgrounds create a frosted-glass depth effect consistent across iOS, Android, and Web.

1.2 What Makes ZynkUp Stand Out

•	Non-blocking I/O: all database queries are awaited asynchronously — zero thread-blocking even under heavy load.

2. High-Level System Architecture
ZynkUp follows a strict Client-Server decoupled architecture. The Flutter frontend never touches the database directly — it strictly consumes JSON APIs and WebSocket streams exposed by FastAPI. This separation allows horizontal scaling, independent deployments, and the ability to add new clients (e.g., a desktop app or third-party integrations) without modifying backend logic.

2.1 Architecture Layers
Layer	Technology & Responsibility
Client Layer	Flutter (Dart) — Handles all UI rendering, local state management, HTTP REST calls, and WebSocket communication. Compiles to native ARM/x86 on mobile and WasmGC on web.
API Gateway / Server	FastAPI (Python) — Async request handler. Validates JWTs on every protected route, executes business logic, reads/writes PostgreSQL, and manages WebSocket connection pools.
Data Layer	PostgreSQL via Supabase — Relational, ACID-compliant. Enforces referential integrity with FK constraints and cascading deletes. Connection pooling via PgBouncer.
Auth Layer	Firebase Auth + Custom JWT — Firebase handles Google OAuth handshake; FastAPI verifies the Firebase ID Token against Google's JWKS endpoint, then issues its own signed JWT embedding user_id and role.
Media Storage	Cloudinary CDN — All binary image data stored externally. PostgreSQL only stores the short URL string, keeping the DB lean and queries fast.
Edge CDN (Web)	Vercel Edge Network — Serves pre-compiled Flutter Web (Wasm/JS) assets over 100+ global PoPs, minimising TTFB for web users.

2.2 Authentication Flow — Hybrid Firebase + Custom JWT
The two-step hybrid model is a common interview focus. Be able to explain each hop clearly:

Step	Actor	Action
1	User → Flutter	User taps Sign in with Google. Flutter initiates Google OAuth via the Firebase SDK.
2	Flutter → Firebase	Firebase authenticates credentials against Google's OAuth 2.0 servers and returns a short-lived Firebase ID Token (RS256-signed JWT, ~1 hour TTL).
3	Flutter → FastAPI	Flutter sends the Firebase ID Token in the Authorization: Bearer header to POST /auth/google.
4	FastAPI → Google JWKS	FastAPI calls firebase_admin.auth.verify_id_token(). Internally, this verifies the token's RS256 signature against Google's public key set (JWKS endpoint), checks exp, iss, and aud claims.
5	FastAPI internally	If valid, FastAPI upserts the user into PostgreSQL (creates account on first login, updates last_seen thereafter). Generates its own HS256-signed JWT embedding {user_id, role, exp}.
6	FastAPI → Flutter	Returns the custom JWT in the response body. Flutter stores it in flutter_secure_storage (iOS Keychain / Android Keystore backed).
7	Subsequent requests	Flutter attaches JWT as Authorization: Bearer {token} on every API call. FastAPI's auth dependency decodes and validates it locally — no external call needed.

Key Interview Insight: The hybrid model delegates the hard parts of OAuth (PKCE flow, token refresh, Google account linking) to Firebase, while the custom JWT gives complete control over role claims, expiry policies, and route-level authorization logic — without an external round-trip on every request.

2.3 Communication Protocols
Protocol	Usage in ZynkUp & Why
HTTPS / REST	All standard API calls: user profiles, event listings, club management, friend requests, XP updates. Stateless, cacheable, and easy to version.
WSS (WebSocket Secure)	Club Chat rooms. Persistent, full-duplex TCP connection. Server pushes messages instantly; no polling overhead. Secured with TLS on the WSS layer.
HTTP Long-Polling (fallback)	Not implemented — WSS with heartbeat ping/pong is preferred. Polling is noted here only as a comparison point for interviews.

4. Backend Deep Dive — FastAPI (Python)
FastAPI is built on Starlette (ASGI web framework) and Pydantic (data validation). It natively supports async/await, automatic OpenAPI documentation, and WebSocket connections — making it the ideal choice for a real-time, concurrent platform like ZynkUp.

4.1 Framework Comparison — FastAPI vs Django vs Flask
Feature	FastAPI (Chosen)	Django	Flask
Concurrency	Fully async (asyncio). Handles thousands of connections on a single thread.	Sync by default; async added later but ecosystem is still largely blocking.	Sync only. One thread per request.
Performance	Benchmarks rival Node.js and Go for I/O-bound workloads.	Significantly slower under concurrent load due to WSGI synchronous model.	Similar to Django under load; WSGI-based.
WebSockets	Native ASGI WebSocket support built in.	Requires Channels package (separate ASGI layer).	Requires external extensions (Flask-SocketIO).
Data Validation	Pydantic: strict typing, auto-reject malformed payloads with 422 errors.	Django Forms / DRF Serializers: powerful but more boilerplate.	Manual validation required; no built-in layer.
Auto Documentation	Swagger UI + ReDoc generated automatically from type hints — zero extra code.	DRF can generate docs but requires extra configuration.	Flask-RESTX or Flasgger required; not native.
ORM	SQLAlchemy (async-compatible with asyncpg).	Built-in Django ORM (synchronous).	SQLAlchemy or Peewee (separate choice).

4.2 Asynchronous I/O — The Core Advantage
The single most important concept to articulate clearly in interviews:

Interview Answer: FastAPI uses Python's asyncio event loop to multiplex connections on a single OS thread. Instead of assigning a dedicated thread to every WebSocket connection (which would exhaust server RAM at scale — 1,000 connections × 1 MB stack = 1 GB RAM), the event loop registers I/O callbacks and parks the coroutine during network waits. When a message arrives on a specific socket, the loop wakes only that coroutine. This makes FastAPI incredibly memory-efficient under concurrent load.

Concept	Synchronous vs Asynchronous Comparison
Thread model	Sync: 1 OS thread blocks waiting for DB query. Async: thread released during await; handles other requests in the meantime.
Memory at 1k connections	Sync (threaded): ~1 GB RAM (1 MB stack × 1,000 threads). Async: ~50 MB (single thread, coroutine state only).
CPU usage	Sync: context-switching overhead between threads. Async: zero context-switch cost; cooperative scheduling.
When async helps	I/O-bound tasks (DB queries, HTTP calls, file reads). Async does NOT speed up CPU-bound work (use multiprocessing for that).

4.3 Pydantic Data Validation
Every incoming request payload is defined as a Pydantic BaseModel. This provides:
•	Automatic type coercion and validation — if event_date is sent as a string, Pydantic attempts to parse it as a datetime.
•	Auto-rejection: missing required fields or wrong types return 422 Unprocessable Entity before route logic executes — no manual if/else checks needed.
•	OpenAPI schema generation: Pydantic models are reflected directly into the auto-generated Swagger docs, keeping documentation always in sync with the actual API.
•	Nested validation: complex structures like lists of attendees or event metadata are validated recursively.

4.4 WebSocket Connection Manager
The backend maintains a singleton ConnectionManager class that acts as an in-memory registry for all active club chat connections:
Operation	Implementation Detail
Data structure	dict[str, list[WebSocket]] — maps club_id (str) to a list of connected WebSocket objects.
connect()	Accepts the WebSocket handshake, appends the object to the club's list, and sends back last-N message history from PostgreSQL.
broadcast()	Iterates all WebSocket objects for a given club_id and calls await ws.send_json(payload). Failed sends are caught individually so one dropped client does not block others.
disconnect()	Removes the WebSocket from the list on close or exception. Triggered by heartbeat failure or explicit client disconnect.
Heartbeat	Server sends a ping frame every 30 seconds. If no pong is received within 10 seconds, the connection is considered dead and removed — preventing zombie sockets from leaking RAM.
Scaling note	This in-memory manager is single-process. For multi-process or multi-server deployment, a Redis Pub/Sub or Kafka broker would be needed to fan out messages across instances.

 
5. Database Design & Schema
ZynkUp's database is structured in Third Normal Form (3NF) to eliminate data redundancy, ensure referential integrity, and allow clean join queries. PostgreSQL is hosted on Supabase for managed backups, row-level security options, and built-in PgBouncer connection pooling.

5.1 Why PostgreSQL over MongoDB?
Aspect	PostgreSQL (Chosen) — Rationale
Data model	Relational — ZynkUp data is inherently relational: Users belong to Clubs, Clubs have Messages, Users have Friends. Relational tables model this naturally with FK constraints.
Consistency	ACID compliance — Atomicity (all-or-nothing transactions), Consistency (FK constraints always enforced), Isolation (concurrent transactions don't see each other's partial state), Durability (committed data survives crashes).
Many-to-Many	Clean resolution via join tables (e.g., club_members). No data duplication; a user's profile is stored once and referenced by club_id + user_id pairs.
Transactions	SELECT ... FOR UPDATE row-level locking handles race conditions (e.g., last event ticket). MongoDB only added multi-document ACID transactions in v4.0 and they carry overhead.
Query power	Complex JOIN queries, window functions, CTEs, and aggregations are native PostgreSQL strengths. MongoDB requires $lookup pipelines which are harder to optimise.

5.2 Core Table Schema
Table	Key Columns	Design Notes
users	id UUID PK, email UNIQUE, name, avatar_url, xp_points INT DEFAULT 0, streak_count INT DEFAULT 0, created_at TIMESTAMPTZ	UUID primary key prevents enumeration attacks. email has UNIQUE constraint. xp_points and streak_count have DEFAULT 0 so no NULL checks needed.
events	id UUID PK, title, description, date TIMESTAMPTZ, location, category, max_attendees INT, creator_id UUID FK→users	creator_id cascades on delete. max_attendees enables the race-condition ticket scenario. category is an ENUM for query filtering.
clubs	id UUID PK, name, description, banner_url, creator_id UUID FK→users, created_at TIMESTAMPTZ	banner_url stores Cloudinary CDN URL. creator_id links to users; club survives if creator is removed (SET NULL on delete).
messages	id UUID PK, club_id UUID FK→clubs, sender_id UUID FK→users, content TEXT, timestamp TIMESTAMPTZ DEFAULT NOW()	Both FKs have CASCADE on delete — deleting a club purges its messages; deleting a user anonymises their messages (SET NULL sender_id).
club_members	user_id UUID FK→users, club_id UUID FK→clubs, role VARCHAR (admin|member), joined_at TIMESTAMPTZ	Composite PK (user_id, club_id) prevents duplicate membership. role stored as constrained VARCHAR with CHECK constraint.
friend_requests	id UUID PK, requester_id UUID FK→users, recipient_id UUID FK→users, status VARCHAR (pending|accepted|declined), created_at	UNIQUE constraint on (requester_id, recipient_id) prevents duplicate requests. status transitions are enforced at the application layer.

5.3 Handling Race Conditions — SELECT FOR UPDATE
Classic systems-design scenario worth preparing for:
Problem: Two users simultaneously register for the last available event ticket. Both read max_attendees = 1 and registered_count = 0. Both insert a registration. Both succeed. The event is oversold.

Solution: Wrap the check-and-decrement in a PostgreSQL transaction with SELECT ... FOR UPDATE. This acquires a row-level exclusive lock on the events row. User A's transaction locks the row, decrements the count to 0, and commits. User B's transaction is blocked until A commits, then reads count = 0 and fails gracefully with a 409 Conflict response.

5.4 Connection Pooling with PgBouncer
PostgreSQL has a hard limit on concurrent connections (~100 by default on Supabase free tier). In a concurrent async environment with many simultaneous requests, each request can open a DB connection. Without pooling, connection limits are hit quickly.
•	Supabase includes PgBouncer in Transaction mode by default.
•	PgBouncer maintains a small pool of actual PostgreSQL connections (e.g., 20) shared across hundreds of application connections.
•	In Transaction mode, a DB connection is borrowed only for the duration of a single transaction, then returned immediately — ideal for async workloads.

7. Advanced Security & Optimisation
7.1 SQL Injection Prevention
Method: SQLAlchemy ORM with parameterised queries exclusively. Raw SQL strings are never concatenated with user input. SQLAlchemy translates Python model operations to parameterised SQL — e.g., session.query(User).filter(User.email == email) becomes SELECT * FROM users WHERE email = $1 with email passed as a bound parameter, not interpolated into the string. This makes SQL injection structurally impossible at the ORM layer.

7.2 Password Security
ZynkUp uses bcrypt with a cost factor of 12 for hashing passwords on email/password accounts (Firebase handles password storage for Google OAuth users). bcrypt is deliberately slow (cost factor doubles hash time per increment), making brute-force attacks computationally prohibitive. Each password hash includes a random salt, preventing rainbow table attacks.

7.3 JWT Security
•	HS256 HMAC signature: the JWT secret key is a 256-bit random value stored in environment secrets. Tampering with the payload invalidates the signature.
•	Short expiry: tokens expire in 24 hours. Refresh token flow can be added for extended sessions without re-login.
•	Role claim in payload: user_id and role are embedded; the server trusts them without a DB query after signature verification.
•	Stored in flutter_secure_storage: uses iOS Keychain / Android Keystore — encrypted at rest, inaccessible to other apps.

7.4 WebSocket Heartbeats — Ping/Pong
TCP connections can silently drop (NAT timeout, mobile network switch, firewall) without either side being notified. ZynkUp implements RFC 6455 WebSocket ping/pong:
•	Server sends a binary Ping frame to each connected client every 30 seconds.
•	The client's WebSocket library automatically responds with a Pong frame.
•	If no Pong is received within a 10-second window, the server closes the socket, removes it from ConnectionManager, and frees the associated memory.
•	This prevents ghost connections from accumulating and consuming RAM on the server.

7.5 Flutter Web File Upload — Browser Security Context
Modern browsers enforce that file picker dialogs can only be opened synchronously within a user-gesture event handler (onClick, onTap). Async operations that happen between the tap and the dialog call (e.g., showing a bottom sheet, awaiting a state update) break this synchronous context, causing browsers to silently block the file picker.
Solution: The file_picker package carefully preserves the synchronous gesture context by calling the native file dialog in the same microtask tick as the user's tap event. Older packages like image_picker break this chain by introducing async gaps, making them unreliable on Flutter Web.

7.6 Flutter WebAssembly (WasmGC) Web Compilation
•	Dart compiles to WebAssembly using the WasmGC garbage-collected memory model — not to JS transpilation.
•	Wasm runs at near-native C++ speeds in the browser, enabling 60 fps Glassmorphism blur animations without dropped frames.
•	Binary size is comparable to JavaScript bundles thanks to Dart's tree-shaking (unused code is stripped at compile time).
•	Wasm modules are loaded via the browser's streaming compilation API — the app starts rendering before the full binary is downloaded.

7.7 Defeating CodeQL Path Traversal (Path Injection) Alerts
Method: When accepting file uploads (e.g., club chat attachments), user-provided input (like filenames or URL path parameters such as `club_id`) can theoretically be manipulated to include directory traversal characters (`../`), allowing attackers to overwrite arbitrary server files. 
Solution: ZynkUp strictly isolates user input from the file system. 
1. We entirely strip user-provided variables (like `club_id`) from the generated filename, relying purely on `uuid.uuid4().hex` for guaranteed uniqueness. 
2. The file extension is extracted, validated against a hardcoded dictionary whitelist, and then assigned from the dictionary literal (e.g., `ext = ALLOWED_EXTS.get(raw_ext, ".bin")`), completely severing the data-flow chain.
3. As a final defense-in-depth measure mandated by CodeQL, we enforce `os.path.abspath(file_path).startswith(os.path.abspath(UPLOAD_DIR))` before saving. This mathematically proves to static analyzers that path injection is structurally impossible.

7.8 Optimising CodeQL Security Scans via .gitattributes
Method: Committing Flutter Web build artifacts (like `build/web/main.dart.js`) causes GitHub Advanced Security (CodeQL) to scan massive, minified Javascript files. This results in false positive alerts (e.g., "Inefficient regular expression" in generated code) and drastically inflates CI/CD pipeline times.
Solution: A `.gitattributes` file is placed in the repository root containing `build/** linguist-generated=true` and `*.dart.js linguist-generated=true`. This explicitly instructs GitHub Linguist and CodeQL to completely ignore these directories during security analysis, keeping the pipeline fast and the security reports focused strictly on handwritten source code.

 
8. Interview Q&A Bank (60+ Questions)
Organised by topic. Each answer is calibrated for a 2–3 minute verbal response. For senior roles, follow up with trade-offs and alternatives.

8.1 Systems Design & Architecture
Q: Why decouple the frontend and backend instead of using server-rendered templates like Django templates or Jinja?
A: Decoupling allows multiple clients — Flutter mobile, Flutter web, or even a future native iOS/Android app — to consume the exact same JSON APIs without any backend changes. It also lets each tier scale independently: I can run 10 FastAPI instances behind a load balancer without changing the Flutter build. Server-rendered templates tightly couple UI to the server, making this impossible.
Q: How does ZynkUp handle thousands of concurrent WebSocket connections without crashing?
A: FastAPI uses Python's asyncio event loop — a single OS thread that multiplexes I/O callbacks. Each WebSocket connection is a coroutine registered with the event loop. Instead of a dedicated OS thread per connection (which consumes ~1 MB stack each), the loop parks inactive coroutines and wakes only the ones with incoming data. At 1,000 connections, the threaded model needs ~1 GB RAM; asyncio needs roughly 50 MB for coroutine state.
Q: How would you scale the WebSocket chat to support multiple backend server instances?
A: The current ConnectionManager is in-process memory — messages sent on Server A can't reach clients connected to Server B. The standard solution is a message broker: Redis Pub/Sub or Kafka. Each server subscribes to a club-specific channel. When a client sends a message, the receiving server publishes it to the broker; all servers subscribed to that club receive it and broadcast to their local connections.
Q: Why use Vercel for the frontend and Render for the backend instead of one provider?
A: Vercel's global Edge CDN is optimised for static asset delivery — it serves compiled JavaScript and Wasm binaries with sub-50 ms TTFB worldwide. Render provides persistent ASGI-compatible containers with always-on TCP connections needed for WebSockets — Vercel's serverless functions terminate after response, so WebSockets are impossible there. Using the best tool for each layer is better than forcing one provider to do both.

8.2 Database & Data Modelling
Q: Why PostgreSQL over MongoDB for ZynkUp?
A: ZynkUp's data is inherently relational: Users belong to many Clubs, Clubs have many Messages from many Users, Users have many Friends. PostgreSQL models this naturally with foreign keys and join tables — no data duplication. MongoDB is document-oriented: storing club membership would require duplicating user data inside club documents or vice versa, creating sync problems. PostgreSQL also gives us ACID transactions for the race-condition ticket scenario.
Q: What is 3NF and how does ZynkUp's schema achieve it?
A: Third Normal Form means every non-key column in a table depends only on the primary key — no partial dependencies (2NF) and no transitive dependencies (3NF). In ZynkUp's schema, the club_members join table only stores user_id, club_id, and role — not the user's name or avatar (which live in users). If a user changes their avatar, there's exactly one row to update. Without 3NF, we'd update every club_members row for that user, risking inconsistency.
Q: What happens if two users register for the last event ticket simultaneously?
A: This is a classic race condition. Both users read max_attendees = 1, registered_count = 0. Both pass the availability check. Both insert a registration. Both succeed — the event is oversold. The fix is a PostgreSQL transaction with SELECT ... FOR UPDATE. User A's transaction locks the events row. User B blocks at the lock. When A commits (count becomes 0), B acquires the lock, re-reads count = 0, and returns 409 Conflict to the user.
Q: Why store image URLs in PostgreSQL instead of binary image data?
A: Storing binary BLOB data in PostgreSQL dramatically inflates row sizes, slows down all queries on the users and clubs tables (even those that don't need the image), and makes the database backup enormous. Cloudinary stores the binary, serves it on a CDN optimised for media delivery (with automatic WebP conversion and responsive resizing), and ZynkUp only stores a short URL string — maybe 100 bytes per row.
Q: How does PgBouncer connection pooling help ZynkUp?
A: PostgreSQL has a hard limit on concurrent connections (~100 on Supabase free tier). An async FastAPI app under load can open hundreds of concurrent DB connections. PgBouncer sits between the app and PostgreSQL, maintaining a small pool of real connections (e.g., 20) shared across all app connections. In Transaction mode, a real DB connection is borrowed only for the duration of one transaction, then returned — perfect for short async queries.

8.3 Backend — FastAPI & Python
Q: What is a JWT and how does ZynkUp use it?
A: A JSON Web Token is a Base64URL-encoded string with three parts: Header (algorithm), Payload (claims like user_id and role), and Signature (HMAC-SHA256 of header + payload using a secret key). ZynkUp's FastAPI embeds the user's UUID and role in the payload, signs it, and returns it to Flutter. On subsequent requests, Flutter sends it back; FastAPI verifies the signature locally — if it matches, the payload is trusted without any database query. Stateless auth.
Q: What is the difference between synchronous and asynchronous Python, and why does it matter?
A: In synchronous Python, when a function awaits a database response, the OS thread blocks and sits idle. In asynchronous Python with asyncio, the coroutine is suspended and the event loop schedules other pending coroutines to run on the same thread. When the DB responds, the original coroutine resumes. This means one thread can handle hundreds of concurrent DB queries without thread-per-request overhead. FastAPI is built async-first; Django's ORM is synchronous by default.
Q: What does Pydantic add over plain Python type hints?
A: Python's type hints are checked by mypy at static analysis time but are ignored at runtime. Pydantic enforces them at runtime — if an incoming JSON payload has a missing required field or a type mismatch, Pydantic raises a ValidationError before route logic runs. FastAPI converts this into a 422 Unprocessable Entity response with a detailed error body. This eliminates hundreds of manual validation if-statements and keeps route functions focused on business logic.
Q: How does the WebSocket ConnectionManager work at the code level?
A: It's a singleton class with a dict mapping club_id (str) to a list of WebSocket objects. The connect() method calls await websocket.accept() and appends the socket. The broadcast() method iterates the club's list and calls await ws.send_json(payload) for each; send errors are caught per-socket so one failure doesn't break others. Disconnect() removes the socket from the list. The heartbeat task runs as an asyncio background task using asyncio.create_task().
Q: How do you prevent SQL injection in ZynkUp?
A: By using SQLAlchemy ORM exclusively — raw SQL strings are never concatenated with user input. SQLAlchemy translates Python expressions like session.query(User).filter(User.email == email) into parameterised queries: SELECT * FROM users WHERE email = $1 with the email value bound separately. The database driver handles escaping; user input never touches the SQL string. This makes injection structurally impossible.

8.4 Frontend — Flutter
Q: How did you fix the dashed-line button bug on Android?
A: The bug was caused by wrapping a TextRun in Flexible inside an OutlinedButton's child. OutlinedButton computes its intrinsic width from its children. Flexible's intrinsicWidth implementation returns 0 — it's designed for row/column flex contexts, not intrinsic sizing. So the button collapsed to 0 pixels wide, triggering TextOverflow.ellipsis, which rendered as three spaced dots looking like dashes. Fix: remove Flexible entirely, apply EdgeInsets.symmetric(horizontal: 16) padding directly on ButtonStyle.
Q: How did you solve file upload on Flutter Web?
A: Browser security policies require file picker dialogs to be triggered synchronously within a user-gesture event handler. If any async operation happens between the tap and the dialog call — like showing a bottom sheet or awaiting a setState — the browser considers the gesture 'consumed' and blocks the dialog. Older packages like image_picker introduce async gaps. The file_picker package triggers the native dialog synchronously in the same microtask tick as the tap event, respecting browser security context on both Chrome and Safari.
Q: How does the Glassmorphism effect work technically?
A: A BackdropFilter widget with ImageFilter.blur(sigmaX: 10, sigmaY: 10) is placed in the widget tree. Flutter's Impeller/Skia renderer blurs everything in the scene rendered behind that layer. A semi-transparent Container (white at ~8% opacity) is layered on top of the blur, creating the frosted-glass effect. A thin Border with white at ~15% opacity simulates light refraction. The entire stack is clipped with ClipRRect for rounded corners.
Q: What is StreamBuilder and why is it used for chat?
A: StreamBuilder is a Flutter widget that listens to a Dart Stream and rebuilds its subtree every time the stream emits a new event. The web_socket_channel package exposes the WebSocket connection as a Stream. When the server broadcasts a new chat message, the stream emits it, and StreamBuilder rebuilds only the chat message list — not the entire screen. This is far more efficient than polling an API every few seconds.
Q: How does flutter_secure_storage differ from shared_preferences?
A: shared_preferences stores data as plaintext in the app's sandbox — accessible if the device is rooted or via developer tools. flutter_secure_storage uses the platform's secure enclave: iOS Keychain (hardware-backed encryption on devices with Secure Enclave) and Android Keystore (hardware-backed on devices with a TEE). JWTs must not be stored in plaintext because a compromised JWT grants full account access until expiry.

8.5 Deployment, DevOps & Security
Q: Why use Split APKs instead of a Fat APK?
A: A Fat APK contains native C++ binaries compiled for every Android CPU architecture: armeabi-v7a (32-bit ARM), arm64-v8a (64-bit ARM), and x86_64 (Intel). Most modern phones are arm64, so they download and discard the other two binaries — wasted 50 MB. flutter build apk --split-per-abi generates three separate APKs, each containing only the binary for that architecture. The arm64-v8a APK is ~25 MB vs ~75 MB for the fat version.
Q: How are API keys and secrets managed securely in ZynkUp?
A: All secrets — JWT secret key, Firebase service account JSON, Cloudinary API key, PostgreSQL connection string — are stored as GitHub Repository Secrets, never hardcoded in source files or .env files committed to the repository. GitHub Actions injects them as environment variables at runtime. Render.com pulls them from its own environment variable configuration panel. The running Docker container reads them via os.getenv() calls.
Q: What is bcrypt and why is it better than SHA-256 for passwords?
A: SHA-256 is a general-purpose hash function designed to be fast — it can hash billions of passwords per second on a GPU, making brute-force attacks trivial. bcrypt is designed to be slow: the cost factor parameter exponentially increases computation time. At cost factor 12, bcrypt takes ~250 ms per hash — 250 ms times billions of password guesses makes brute-force computationally infeasible. bcrypt also includes a built-in random salt, defeating precomputed rainbow tables.
Q: How would you add rate limiting to ZynkUp's API?
A: I would add a SlowAPI middleware (built on limits library) to FastAPI. Rate limits are applied per IP or per user_id (extracted from JWT) on sensitive endpoints — e.g., 5 requests/minute on POST /auth/login to prevent credential stuffing, 100 requests/minute on GET /events for normal usage. At scale, a Redis backend would store the rate limit counters so limits are shared across multiple FastAPI instances.
Q: How do you handle file upload security and prevent path traversal (Directory Traversal) attacks?
A: In ZynkUp, we strictly isolate user input from the file system. First, we never use the user's original filename. We generate a universally unique name using `uuid.uuid4().hex`. If we need the file extension, we extract it, validate it against a hardcoded whitelist, and then map it to a literal string from our dictionary — breaking any data-flow from the HTTP request to the file system. Finally, before calling `open()`, we use `os.path.abspath()` to verify that the final destination path strictly starts with the absolute path of our dedicated upload directory. This approach fully satisfies strict static analysis engines like CodeQL.
Q: How do you manage false positives in automated security scanning like GitHub CodeQL?
A: When deploying Flutter Web, massive generated files like `main.dart.js` are often caught by CodeQL, triggering false positives like "Inefficient regular expression" on code we didn't write. To resolve this without disabling the scanner, we use a `.gitattributes` file to mark `build/**` and `*.dart.js` as `linguist-generated=true`. CodeQL respects this directive, automatically excluding generated artifacts from its analysis. This keeps the CI pipeline fast and ensures security alerts only flag actionable issues in our actual source code.

9.2 Key Concepts — One-Line Definitions
Concept	Definition
JWT (JSON Web Token)	Header + Payload + HMAC Signature. Stateless auth: verify signature locally, trust payload claims without a DB query.
WebSocket vs Polling	WebSocket: server pushes data instantly over persistent TCP. Polling: client asks the server repeatedly every N seconds — wasteful and adds latency.
Async vs Sync (Python)	Async: thread released during I/O wait (await); other coroutines run. Sync: thread blocks idle during I/O wait; can only do one thing at a time.
3NF (Third Normal Form)	Database normalisation rule: every non-key column depends only on the primary key. No partial or transitive dependencies. Eliminates data duplication.
Join Table	Resolves Many-to-Many relationships: club_members(user_id, club_id, role) links Users to Clubs without duplicating either entity's data.
bcrypt	Slow password hashing algorithm with tunable cost factor and built-in salt. Designed to make brute-force GPU attacks computationally infeasible.
PgBouncer	Connection pooler: maintains a small pool of real DB connections shared across many application connections. Prevents exhausting PostgreSQL connection limits.
SELECT FOR UPDATE	PostgreSQL row-level lock that prevents concurrent transactions from reading a stale value during a check-then-act operation (e.g., last ticket).
Intrinsic Width	The natural space a Flutter widget requests for itself. Flexible returns 0 intrinsic width, causing layout collapse inside OutlinedButton.
WasmGC	WebAssembly Garbage Collection — Dart's browser compilation target. Runs at near-native speeds vs JavaScript transpilation, enabling smooth Glassmorphism.
Split APK	Architecture-specific Android build. Strips unused CPU binaries. Reduces arm64 download size from ~75 MB (Fat APK) to ~25 MB.
BackdropFilter	Flutter widget that applies a filter (blur, colour colour matrix) to everything rendered behind it in the scene — the core of Glassmorphism implementation.
Path Traversal (Injection)	A vulnerability where an attacker manipulates file paths (e.g., using `../`) to access or overwrite unauthorized files. Prevented by stripping user input and using `os.path.abspath()` validation.
.gitattributes (linguist-generated)	A Git configuration flag that tells GitHub (and tools like CodeQL) that a file is auto-generated, excluding it from language statistics and security scans.
